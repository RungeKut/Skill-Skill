# Работа с репозиторием

Набор — публичный репозиторий `RungeKut/<Имя>-Skill`, ветка `main`;
разворачивается на нескольких машинах и у нескольких агентов. Всё
закоммиченное пригодно для публикации, даже если репозиторий закрыт.

## Порядок

```bash
git -C "<корень>" pull --rebase              # в НАЧАЛЕ; конфликт — разобрать до работы
# ... правка ...
git diff                                     # прочитать глазами
python tools/check_docs.py --project "<папка проекта>"
git add <файлы>                              # не -A: тянет лишнее
git commit -m "что и почему"
git push                                     # СРАЗУ после правки
```

* Шаг = коммит. Amend — только неотправленного; отправленный правится
  новым коммитом.
* Push отклонён — `git pull --rebase`, затем `check_docs.py` заново и
  перечитать слитое (git сливает текст, а не смысл), потом push.
* Push не сделан (нет сети, нет права) — в конце сессии назвать число
  неотправленных коммитов (`check_docs.py` печатает его).
* Удаление файлов, перепись истории, `push --force` — только по команде
  человека.

## Обезличивание

Набор — знание об инструменте. В файлы, текст коммита, заголовок и текст PR
не попадает ничего, по чему узнаётся рабочий проект:

* названия изделий и проектов, децимальные номера, имена файлов и папок
  проектов, репозиториев;
* пути, имена машин и серверов, учётные записи, корпоративные адреса
  почты, имена людей (источник записи — метка вида `P-nn`, если нужна);
* **снимки окон рабочих программ**: на картинке читаются имена и данные, а
  стоп-лист картинки не видит. Снимки живут во временной папке сессии или
  в игнорируемой папке набора; изображения под git — только `examples/`, и
  только на программах из поставки ОС и отвлечённых данных;
* доменное — по списку набора в его 40-02 (узлы, цепи, имена моделей,
  классы окон закрытых программ…).

Остаётся: поведение программ, вызовы, ловушки, примеры на отвлечённых
данных. Описание, по которому проект узнаётся без названия, не ловит
никакая проверка — за этим `git diff` глазами.

### Стоп-лист

Общий — `skill-skill/tools/stoplist.txt`, свой набора — `tools/stoplist.txt`;
оба **локальные** (в `.gitignore`), у каждой машины свои: стоп-лист в
публичном репозитории сам публикует то, что скрывает. Новый проект — строка
в стоп-лист **до** первого коммита. Сверяют: `check_docs.py` — все тексты и
историю, хук `commit-msg` — сообщение. `--project "<папка>"` и
`git config <name>.project "<папка>"` добавляют слова имени папки проекта.
Локальные реестры проектов — в `local/` (тоже не под git).

**Стоп-лист не хранить в облаке** и в синхронизируемой папке (OneDrive,
Яндекс Диск, общий диск) — та же утечка, что и в репозитории: список
названий лежит у постороннего сервиса. На другую машину он переносится
руками или не переносится вовсе — там свои проекты.

### Чего проверка не видит

| Дыра | Почему | Чем закрыто |
|---|---|---|
| Описание, по которому проект узнаётся без названия | слов из стоп-листа нет | только `git diff` глазами и обезличивание отдельным шагом (00) |
| Новый проект, не вписанный в стоп-лист | сверять не с чем | строка в стоп-лист до первого коммита |
| Слово в другой форме: падеж, сокращение, транслит | сравнение — подстрокой | в стоп-лист — основа слова и варианты |
| Снимки окон, PDF, документы Office | читаются только текстовые расширения | изображения — только `examples/`; прочее — глазами |
| Автор и коммитер | хук видит только текст сообщения | `check_docs.py`: автор клона и история |
| `--no-verify`, коммит на машине без хука | хук не запускался | `check_docs.py` смотрит историю |
| Старые коммиты | файл исправлен, история нет | только перепись истории по команде владельца |
| Конфликт, разрешённый при слиянии | в `git log -p` правки слияния не видны | перечитать слитое после merge |
| Сам стоп-лист под git или в облаке | публикует все названия списком | `check_docs.py` ловит его под git; облако — правило выше |

Прежние дыры, закрытые после утечек: проверка смотрела только
`knowledge/` (название ушло через `CHANGELOG.md`), сравнивала с учётом
регистра, не смотрела текст коммита, стоп-лист лежал в публичном
репозитории, без автора клона git подставлял глобальные рабочие имя и
адрес (SolidWorks-Skill, 40-02).

## Автор и соавторы

```bash
git config user.name  "<публичное имя>"     # без --global, для клона
git config user.email "<публичный адрес>"
```

* Автор коммита — публичное имя того, кто его сделал, заданное для клона.
  Не задан — **не коммитить, спросить человека**: иначе git возьмёт
  глобальные (на рабочей машине — рабочие) имя и адрес.
* **Без соавторов**: ни строк-подписей `…-by:` (соавторы, Signed-off-by),
  ни «Generated with», ни 🤖, ни noreply-адресов ИИ (30-04). Упоминать агентов как тему записи можно.
* Хук `commit-msg` — общий, в skill-skill (`core.hooksPath
  ../skill-skill/hooks`, 40-01); `--no-verify` не спасает — историю
  проверяет `check_docs.py`.

## Вклад без права записи: форк и PR

Push отклонён с `403` / `Permission denied` — право записи только у
владельца; доступ не подбирать. Так же `403` на слияние PR через REST
(`PUT /repos/{owner}/{repo}/pulls/{N}/merge`) значит: **вы не владелец** —
не сливать, оставить PR владельцу (а владелец сливает не через API, а
локально, ниже).

```bash
gh repo fork RungeKut/<Имя>-Skill --remote --remote-name=fork
git switch -c <тема-латиницей>
# правка; тот же порядок: diff глазами, check_docs.py, чистые сообщения
git push fork <тема-латиницей>
gh pr create --repo RungeKut/<Имя>-Skill --title "что и почему" \
     --body "check_docs.py — расхождений нет; <суть>"
```

Один PR — одна тема. Свой PR не сливать. Без `gh` — REST API (40-03).

## Владельцу: разбор PR

Принимает только владелец (с помощью ИИ), в начале работы вместе с pull:

```bash
gh pr list                                   # пусто — работаем дальше
git fetch origin pull/<N>/head:pr-<N>
git diff main...pr-<N>                       # целиком, глазами
git log --format='%an <%ae>%n%B' main..pr-<N>   # сообщения и авторы — по правилам выше
git switch pr-<N> && python tools/check_docs.py && git switch main
git merge --no-ff pr-<N>
git push
```

* Без squash (GitHub дописывает соавторов, 30-03), без rebase и
  cherry-pick: коммиты автора PR остаются с его авторством, история
  прозрачная.
* **Особое внимание исполняемым файлам** (`*.py`, хуки, скрипты): после
  слияния они запускаются на машине владельца.
* Не прошло — не сливать, вернуть с пояснением:
  `gh pr review <N> --request-changes --body "что поправить"`; автор правит
  у себя. «Слить и поправить потом» нельзя: содержимое публично сразу.
